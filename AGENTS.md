# Repository Guidelines

## Структура проекта и организация модулей

Рабочая область объединяет проектные материалы, библиотеку компонентов и референсные реализации. Общей сборки приложения в корне пока нет.

- `docs/README.md`: обзор спецификации и порядок чтения.
- `docs/adr/`: архитектурные решения и предложения с явными статусами.
- `docs/rules/`: требования, критерии приёмки и реестр сценариев.
- `docs/sources/`: исходные бриф, презентация и SVG-карта сценариев.
- `ui-kit/`: общий UI Kit на QML/C++ для Qt 6 для собственной оболочки SberOS и приложений её экосистемы. Общие компоненты, тема, типографика, размеры, иконки и визуальные состояния развиваются здесь и переиспользуются оболочкой и приложениями; логика рабочего стола и предметная логика приложений остаются в соответствующих проектах. Основные модули: `core/`, `controls/`, `theme/`, `utils/` и `widgets/`. Переводы находятся в `po/`, файлы пакетирования — в `debian/`, тесты — в `tests/`.
- `shell/`: базовый код оболочки для дальнейшей адаптации под SberOS. Это исходный снимок Sirca Shell без Git-метаданных. Перед изменениями изучите его README и локальные инструкции, сохраняйте лицензии и авторство.
- `refs/NextKde/`: альтернативная референсная реализация; используйте для сравнения архитектурных решений.

Перед изменением поведения оболочки прочитайте [обзор спецификации](docs/README.md), применимые правила в `docs/rules/` и статусы ADR в `docs/adr/`. В задачах и проверках указывайте ID затронутых сценариев.

Вносите изменения в соответствующий проект. Сохраняйте сторонние лицензии и сведения о происхождении ресурсов.

По необходимости сверяйте изменения с применимыми правилами в `docs/rules/`,
README затронутого проекта и действующими ADR. Перед изменением проверяйте
ограничения и принятые решения; после — согласованность результата с документацией.
Если изменились поведение, API, зависимости, сборка, запуск или архитектурные решения,
обновляйте соответствующие документы в той же задаче. Не перечитывайте всю
документацию для каждой мелкой правки: выбирайте документы по области изменения.


## API-контракт UI Kit

При использовании UI Kit в оболочке и приложениях основной источник —
[API-контракт](ui-kit/docs/API.md). Свойства, сигналы и базовые типы ищите
в [каталоге объявлений](ui-kit/docs/API-catalog.md), цвета, размеры и шрифты —
в [каталоге токенов](ui-kit/docs/API-tokens.md). Не перечитывайте реализацию
библиотеки для обычного использования описанного API.

Если контракта недостаточно, возникла ошибка или проверка актуальности не проходит,
изучите только относящиеся к вопросу исходники и дополните контракт в той же задаче.
При изменении самой библиотеки читайте код по необходимости; вместе с изменением
обновляйте контракт и каталоги. Проверка из корня: `python3 ui-kit/tools/api_contract.py --check`.
После проверки смысла изменений перегенерация: `python3 ui-kit/tools/api_contract.py --write`.
Эта проверка не заменяет сборку, тесты поведения и визуальную проверку.


## Команды сборки, тестирования и разработки

Для `shell/` и библиотеки компонентов действуют отдельные сборки. Перед сборкой оболочки изучите `shell/README.md` и `shell/shell/README.md`; проект также содержит установщик, поэтому для разработки сначала используйте его документированный режим разработки. Команды библиотеки выполняйте из `ui-kit/` с установленными CMake, зависимостями Qt 6, включая Qt Test:

```sh
export CXX=/usr/bin/clang++
cmake -S . -B _build -DBUILD_WITH_CTEST=ON
cmake --build _build -j
ctest --test-dir _build --output-on-failure
```

Команды последовательно настраивают, собирают и тестируют библиотеку. Её README рекомендует Clang. Команда `cmake --install _build` устанавливает библиотеку; сначала проверьте пути установки, поскольку по умолчанию используется `/usr`. У референсных проектов собственные процедуры. NextKde требует выполнять сборку, тестирование и графические проверки в отдельной виртуальной машине или CI.

## Стиль кода и соглашения об именовании

Следуйте стилю соседнего кода. В QML используйте отступы в четыре пробела, PascalCase для файлов компонентов (`Button.qml`) и camelCase для свойств и идентификаторов. Имена файлов C++ обычно записаны в snake_case (`app_screen.cpp`). Сохраняйте форматирование соответствующего модуля. Общих настроек форматирования и линтинга нет; избегайте изменений оформления, не связанных с задачей.

## Правила тестирования

Библиотека использует Qt Test через CTest. Добавляйте тесты в `tests/` с именами `test_<behavior>.cpp` и регистрируйте их в `CMakeLists.txt` этого каталога. Существующий тест `test_plugin_load` проверяет загрузку плагинов и имеет метки `abi` и `smoke`. Порог покрытия не задан. Для визуальных изменений прикладывайте скриншоты и указывайте версию Qt и окружение рабочего стола, использованные при проверке.

### Короткий порядок проверки

- Сначала проверяйте изменённый компонент изолированно. Для настроек: `python3 shell/shell/tests/run-settings-tests.py --output /tmp/sber-settings-check` из корня; сервисы подставные, конфигурация рабочего стола не меняется.
- После изменения UI Kit: сборка библиотеки и `python3 ui-kit/tools/api_contract.py --check`. После изменения оболочки: сборка `shell/shell/`. Запускайте применимые тесты; отсутствие зависимости Qt Test не считать успешным CTest.
- Для визуальных изменений сохраняйте скриншоты до/после в обеих темах; указывайте версию Qt, платформу и ID сценариев. `offscreen` не подтверждает работу Wayland-интеграций.
- По просьбе показать настройки запускайте отдельный предпросмотр; явно сообщайте, если сервисы подставные. Полную оболочку запускайте по просьбе пользователя напрямую из собранного бинарника, без установщика, `sirca-shell-switch on` и `--own-launcher-key`, если переключение сессии отдельно не запрошено.
- При запуске GUI сохраняйте PID или ID exec-сессии и сообщайте результат запуска. По команде «выключи» / «останови» сразу завершайте именно запущенный процесс через сохранённую сессию или PID, без повторных согласований и поиска способа остановки. Не завершайте чужие процессы по общему имени.
- Ограничивайте общие проверки таймаутом. `sirca-shell --check` ранее зависал в offscreen: используйте `timeout 25s`, таймаут отмечайте как незавершённую проверку, не повторяйте без нового основания.
- В результате кратко указывайте: что проверено, что прошло и что осталось непроверенным. Запуск GUI подтверждайте по журналу, визуальную корректность — просмотром снимков или окна.

## Коммиты и запросы на слияние

Репозиторий Git инициализирован. После каждой завершённой и проверенной доработки создавайте отдельный коммит, чтобы сохранять историю изменений. Перед коммитом проверяйте состав diff; не включайте посторонние изменения, сборки и локальные данные. В сообщении или описании фиксируйте существенные ограничения проверок. Пишите короткие заголовки в повелительном наклонении с указанием затронутого модуля. Каждый коммит должен решать одну задачу. В запросе на слияние опишите изменение, добавьте ссылки на задачи или спецификации, перечислите команды проверки и результаты, отметьте пропущенные проверки. Для изменений интерфейса приложите скриншоты до и после.
