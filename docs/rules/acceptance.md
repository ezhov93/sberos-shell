# Приёмка и метрики

Источник: [бриф](../sources/brif_DE.odt), раздел 5; [презентация](../sources/SberOS_DE.pptx), слайды 7, 9, 12.

| Критерий | Требуемое подтверждение |
| --- | --- |
| Стабильность | Снижение пользовательски значимых сбоев на 1000 часов относительно исходной GNOME-среды |
| Непрерывность | Снижение вынужденных перезапусков графической сессии из-за ошибок интерфейса |
| Сохранение опыта | 100% критичных сценариев доступны и проходят проверку; нет значимых ухудшений |
| Совместимость | Все обязательные корпоративные приложения и целевые аппаратные конфигурации проходят испытания |
| Управляемость | Внешние обновления не меняют согласованные сценарии незапланированно |
| AI | Ключевые операции документированы в API и безопасно вызываются агентом |
| Wayland | Все поддерживаемые сценарии работают и тестируются в единой Wayland-сессии |
| Сопровождение | Снижение трудозатрат на интеграцию и устранение регрессий |

Числовые цели снижения сбоев и затрат определяются после измерения исходных показателей. Не придумывать проценты, SLA, сроки восстановления или целевые задержки. Перечни обязательных приложений и оборудования ещё нужно определить.

## Визуальная приёмка MVP

По решению пользователя от 2026-10-25 показанные в [HTML-моке](../mock/smart-panel/index.html)
поверхности MVP должны соответствовать его композиции, геометрии, графике,
прозрачности, blur и визуальным состояниям. Полная матрица и приоритет источников —
[в правилах сверки](mock-parity.md), основание — [ADR-0011](../adr/0011-mock-visual-target.md).

Приёмку проводить отдельно для Sirca и Quickshell: одинаковое состояние при
1920×1080, тема, масштаб/DPR и обои, снимки до/после и перечень расхождений.
Работающий процесс и успешная сборка сами по себе не подтверждают сходство.
Реальные системные сценарии проходят отдельную проверку по FT/ID сценариев;
демонстрационные данные и сообщения HTML не заменяют интеграции.

## Формат доказательств для изменений

Следующее — соглашение этой документации для проверяемой работы агента:

1. Перечислить затронутые ID сценариев и межсценарные зависимости.
2. Указать версию сборки, окружение, приложения и оборудование.
3. Описать действия, ожидаемый минимум и фактический результат.
4. Отдельно перечислить пропущенные проверки, известные ограничения и будущие возможности.

Успех прототипа не подтверждает готовность всей DE. Для Go/No-Go сравнить альтернативы по качеству, стоимости владения, совместимости, мониторам, доступности, сопровождению, рискам и срокам. Возможность внешнего продукта остаётся гипотезой.
