# QS-001: Упростить оформление Quickshell-реализации SberOS

- **Статус:** В работе
- **Обновлено:** 2026-10-25
- **Источник:** прямой запрос пользователя от 2026-10-22: удалить из реализации DE возможности NextKDE, которые не нужны SberOS; разрешено исследовать исходники.
- **Уточнение пользователя:** удалить нецелевые стилевые пресеты NextKDE и закрепить палитру UI Kit; светлую и тёмную схемы сохранить. Поверхности, представленные в моке, теперь оформляются по ADR-0011.
- **Уточнение пользователя от 2026-10-22:** обратную совместимость со старым оформлением не сохранять; legacy-код удалять сразу, без миграций и алиасов.
- **Область:** рабочая копия `quickshell/`; `refs/NextKde/` остаётся неизменным сравнительным эталоном.
- **Связанные требования:** SHELL-001, ADR-0009, ADR-0011, UI Kit API и токены.
- **Сценарии:** `09-01`, `09-02`, `09-19`, `09-21`, `09-24`; применимые сценарии интерфейса уточнить по затронутым поверхностям.
- **Зависимости:** PANEL-010, SHELL-001.

## Цель и границы

Привести Quickshell-копию к оформлению SberOS: единая палитра UI Kit,
поверхности из HTML-мока с прозрачностью и blur, без переключаемых визуальных
пресетов macOS/Windows/Material. Удалённые пользовательские настройки и пресеты
Glass не возвращать: blur — часть материала целевых поверхностей, а не отдельный
режим оформления. Сохранить светлую и тёмную схемы и системные функции,
подтверждённые сценариями оболочки. При удалении legacy-оформления не сохранять
совместимость: удалить старые поля конфигурации, миграции, алиасы и fallback-ветки.
Не удалять модули только по факту их наличия в NextKDE: сначала сопоставить функцию
со сценариями. Стеклянные KWin-плагины, виджеты и обои рассматривать отдельно от
обязательных функций панели, запуска, окон, уведомлений и системного управления.

## Предварительная инвентаризация

Подтверждены крупные области: `AppearanceConfigService.qml` и `AppearanceTokens.qml`,
страница `ThemeSettingsPage.qml`, настройки/IPC в `apps/settings` и
`DesktopEnvironment.qml`, QML-компоненты `shared/qml/controls` и
`modules/common`, KWin `glass-effect`, визуальные поверхности панели/Launcher/Dock,
цветизация обоев, пространственные обои и модуль Spatial3D. Наличие пространственных
обоев и виджетов само по себе не доказывает, что их надо удалить: отдельно проверить
их связь с пользовательскими сценариями и решениями проекта.

Открытый продуктовый вопрос: `WindowAnimationSettingsPage` предлагает режим иконок

пресетам Shell; применимого решения в ADR/правилах не найдено. Поведение не менялось
без подтверждённого требования.

Поиск по исходникам подтвердил, что удаления одного переключателя Theme недостаточно:

остаётся отдельным compositor effect; production Shell не объявляет SurfaceShape.

## Проверки и результат

Прежний этап с непрозрачными поверхностями зафиксирован как промежуточный результат.
После решения ADR-0011 он не закрывает соответствие визуальной цели; поверхности,
показанные в моке, требуется привести к прозрачности/blur отдельно от удаления
переключаемых Glass-пресетов.

Для инвентаризации выполнен поиск по QML/C++/JS потребителям `shellStyle`,
`barMacStyle`, `glassStyle`, `LiquidGlassPanel`, `BackgroundEffect.blurRegion`
и токенам форм. Найдены отдельные владельцы выбора в Settings и Shell, собственные
поверхности Shell, а также KWin/window-appearance зависимости за пределами
оформления панелей. Обновлена карта потребителей и границы удаления выше.

Исходная копия `refs/NextKde/` чистая и хранит собственную историю Git. В рабочем
дереве до этой задачи уже были незакоммиченные изменения `AGENTS.md`,
`docs/tasks/README.md`, `docs/tasks/PANEL-010.md`, а также новые каталоги
`quickshell/` и `refs/`; они не принадлежат этой задаче и не включаются в её diff
без отдельной сверки. По прямому запросу пользователя ограничение проверок только
ограничение на способ проверки удалено из корневых и Quickshell-инструкций.

Основная рамка окна Quickshell-настроек частично переведена на `Sber.Theme`.
После визуальной проверки пользователь сообщил, что Shell-поверхности прозрачны,
а их цвета не совпадают с темой. Политика `AppearanceTokens.surface` теперь
использует непрозрачные заливки из `Theme.Palette`, отключает KWin blur/refraction,
а эффективный режим `AppearanceConfigService` синхронизируется с `Core.Settings`.
Пункт прозрачной раскладки Bar удалён из выбора; оставшуюся миграцию старого значения
теперь также требуется удалить. Переключатели пресетов и связанные старые значения
конфигурации ещё предстоит удалить без миграции. В предпросмотре обнаружен нераспознанный
обработчик `ThemeChanged`; его удалили, а revision для перерисовки теперь
увеличивается при смене светлого/тёмного режима. После перезапуска пользователь
оценил цвета как «пока сойдет»; это предварительное принятие текущего результата,
не завершённая проверка всех поверхностей и состояний. Пользователь уточнил, что
совместимость со старым оформлением не нужна: поля, миграции, алиасы и UI legacy-
режимов должны удаляться вместе с потребителями.

Продолжение 2026-10-22: Settings больше не показывает переключатели macOS/Material,
Glass-параметры или Glass Debug; отдельные Display/Glass Debug страницы и mac-стиль
Bar удалены. C++ appearance bridge и Quickshell IPC оставляют только поддержанные
настройки. `AppearanceConfigService` читает только текущие поля без миграции,
`IconAppearanceService` читает только собственный файл и точные ключи схемы.
Тестовые цели, утверждавшие старые формы, миграцию и стеклянную палитру, удалены.
Bar и токены поверхностей переведены на сплошные заливки; статические blur/liquid
значения больше не являются настройками.

Проверки: `git diff --check` прошёл. `cmake --build .build/kosctl -j2` завершился
успешно; доступная конфигурация собирает Settings/platform-цели и не включает
полную QML-сборку Shell. Тесты и визуальную проверку в этом продолжении не запускал.
На тот момент оставались потребители и реализация `LiquidGlassPanel`; они удалены в
продолжении ниже. До визуальной проверки непрозрачности всех поверхностей в обеих
темах критерии задачи не закрыты.

Путь для разработки: `kosctl dev`/`kosctl settings` добавляют каталог QML-сборки
UI Kit в `QML_IMPORT_PATH`, если он существует. `kosctl build` собирает UI Kit в
`.build/kosctl/ui-kit`, а deploy размещает модули и ресурсы в управляемом
пользовательском runtime и настраивает import path Shell/Settings. Плагины получают
относительный RUNPATH для соседних модулей. В UI Kit реализован поиск ресурсов
через `SBER_COMPONENTS_DATA_DIR`, checkout-каталог для разработки и стандартный
`share/SberComponents`. Сборка UI Kit, отдельная сборка `kos-settings`, полная
сборка `kosctl build` (с отключёнными KWin-плагинами и Spatial3D) и проверка
API-контракта прошли. После запуска из графической сессии с доступом к Wayland
предпросмотр подтвердил загрузку Shell-конфигурации; запуск через обычный sandbox
до этого блокировался доступом к `/run/user/1000` и Wayland/X11. После повторного
запуска ошибок QML палитры не обнаружено. В предпросмотре нет platform/data service
sockets, поэтому системные действия и сохранение настроек ограничены. Пользователь
заметил прозрачность поверхностей; заливки переведены на `Theme.Palette`, цвета
предварительно приняты. Установленный запуск без исходного дерева и CTest не
проверялись.
Уточнён API-контракт: в CMake Quickshell нет параметра `SBER_QML_IMPORT_PATH`,
ранее ошибочно указанного в `ui-kit/docs/API.md`.

## Следующий шаг

Следующий шаг: проверить основные поверхности и состояния в светлой и тёмной темах,
затем проверить установленный запуск без исходного дерева. После выполнения этих
проверок пересмотреть оставшиеся критерии QS-001.

Продолжение 2026-10-23 (контраст текста в меню): во время предпросмотра выявлены
`ReferenceError: ThemeService is not defined` в `OpaqueSurface` и `KosFloatPanel`:
общий модуль ссылался на singleton из Dock без импорта, из-за чего часть foreground
не задавалась. У поверхностей foreground роли теперь берутся из `AppearanceTokens`,
который выбирает UI Kit `Text.OnDark`/`Text.OnLight` по теме. Preview перезапущен,
конфигурация загрузилась; в свежем выводе нет `ReferenceError`/ошибок привязок.
