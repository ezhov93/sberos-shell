# ATP-001: выбор способа раскрытия острова приложений

27.10.2026. Источник — обсуждение пользователя: расширить виджет вместо отдельного
popup, сохранив размеры развёрнутых окон. Сценарии `03-01`, `03-14`–`03-18`,
`03-22`, `09-24`; `FT_SMART_PANEL_APPLICATIONS_11–15`, `UI_SMART_PANEL_APPLICATIONS_9–12`.

Это исследование механизма размещения. Рабочая реализация +N не изменена,
вариант ещё не принят отдельным решением пользователя.

## Окружение и воспроизведение

Qt 6.11.2 / Plasma 6.7.4, виртуальный KWin/Wayland 1920×1080, DPR 1,
Breeze Light. Два настоящих клиента QML: развёрнутое окно без рамки и отдельное
fullscreen-окно. Размеры клиента читаются из QWindow, фактическая геометрия
поверхностей — независимым read-only KWin script через frameGeometry.

```sh
python3 plasma-theme/tests/probe-panel-expansion.py --source plasma-theme \
  --output /tmp/sber-expansion-check
```

Скрипт копирует KPackage в отдельный XDG-профиль, запускает private D-Bus/KWin,
инструментирует только временную копию Panel.qml и завершает свою группу процессов.
Сценарии меняют только толщину/размеры тестовой панели; основной сеанс не меняется.
Фиксируются 11 состояний с выдержкой 1600 ms после изменения.
Для воспроизведения нужны KDE runtime, qml, qdbus6 и доступ для запуска KWin.
В текущем sandbox последнего нет; запуск выполнен с необходимым доступом.

Полные измерения: [geometry.json](geometry.json). QWindow и frameGeometry KWin

о сдвиге относится прежде всего к развёрнутым окнам, использующим рабочую область.

## Вывод по вариантам

1. **Изменить thickness 88 → 168.** Уменьшает развёрнутое приложение
   1920×992 → 1920×912. Для раскрытия острова этот вариант не подходит.
2. **Изменить только QWindow.height.** Размер приложения сохраняется, но KWin
   оставляет панель в y=992 при высоте 168: низ оказывается в y=1160 за экраном.
   Ручное QWindow.y=912 меняет клиентское представление координат, но KWin
   оставляет поверхность в y=992. После штатного пересчёта геометрии через offset
   значение Qt снова становится y=992. Это не рабочее расширение вверх.
3. **Использовать внутренние fixedTopFloatingPadding/updateFloating.** Получается
   корректная поверхность панели y=912, h=168 с резервом KWin 88 px: приложение
   остаётся 1920×992. Однако Plasma сообщает availableScreenRect.height=912.
   Два контракта рабочего места расходятся; это внутренний механизм floating,
   поддержка которого удалена из проекта. Вариант требует дополнительной
   интеграции и проверки popup, рабочего стола, масок и смены экрана.
4. **Отдельная поверхность с наложением на остров.** Существующий native popup
   smarttasks переведён в overlapPanel=true в тестовой копии. Панель остаётся
   1920×88 в y=992, Plasma сообщает 1920×992, развёрнутый клиент — 1920×992,
   fullscreen — 1920×1080. Окно раскрытия — 504×168 в (152,904), его нижний край
   совпадает с нижним краем исходного острова (1072).

**Рекомендация исследования:** четвёртый вариант проще встроить в существующий
QML/KPackage-проект. Следующая доработка — перенести в окно весь остров вместе
с настоящей кнопкой Drawer/Launchpad, убрать дублирующий компактный ряд и общий
нижний фон на время раскрытия. Для пользователя это должна быть одна растущая
поверхность. Проверка подтверждает независимость рабочего места от окна раскрытия,
а не завершённость такого общего острова или правильность анимации.

## Источники и пределы

Проверены исходники точно установленной версии:

- [PanelView 6.7.4](https://github.com/KDE/plasma-workspace/blob/v6.7.4/shell/panelview.cpp):
  preferredSize/geometryByDistance используют totalThickness; updateExclusiveZone
  в NormalPanel передаёт thickness; updateFloating читает внутренние поля QML.
- [API PanelView](https://github.com/KDE/plasma-workspace/blob/v6.7.4/shell/panelview.h):
  отдельного QML-свойства для произвольного резерва нет.
- [ShellCorona 6.7.4](https://github.com/KDE/plasma-workspace/blob/v6.7.4/shell/shellcorona.cpp):
  расчёт доступной области учитывает totalThickness.
- [KWin scripting API](https://develop.kde.org/docs/plasma/kwin/api/):
  независимое чтение frameGeometry.

Просмотрены QML-снимки [исходного ряда](baseline.png),
[увеличенного окна](window-height.png) и [варианта с полем](extra-padding.png).
Они показывают содержимое QML через grabToImage; геометрию на экране подтверждает
frameGeometry KWin, а не эти снимки. Они не подтверждают композицию blur или
порядок поверхностей над настоящим fullscreen.

Автоматические проверки прошли: исходная высота клиента 992, контрольное уменьшение
до 912, постоянные 1080 у fullscreen, неизменность клиента/рабочей области/панели
при раскрытии отдельной поверхности, воспроизведение обрезки прямого resize и
расхождения варианта с полями. Python синтаксис и git diff --check прошли.

Группы процессов: 142219 (первый запуск с ошибкой синтаксиса инструментирования,
не используется как доказательство), 142757 (предварительный), 143925 (итоговый).
Все завершены. Пользовательские файлы и основной сервис этим исследованием не менялись.
Реальный ввод, клики сквозь прозрачные области, фокус, hotplug, другие разрешения,
тёмная тема и положение поверх fullscreen этим опытом не проверены.
